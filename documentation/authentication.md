# Authentication

The CMS uses two separate authentication models depending on which system you are calling.

## 1. CMS web application (session)

Used by: browser UI, internal JSON endpoints (`/articles/images`, `/sites/{id}/authors`, etc.)

### Login

```http
POST /login
Content-Type: application/x-www-form-urlencoded
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `email` | string | Yes | User email address |
| `password` | string | Yes | User password |
| `remember` | boolean | No | Persistent session when checked |

**Success:** `302` redirect to dashboard (or intended page).

**Failure:** `302` back to login with validation errors. Login is rate-limited to **5 attempts** per email/IP combination.

### Session

- Guard: `web` (session driver, default: database).
- Session lifetime: **120 minutes** (configurable in `config/session.php`).
- All authenticated routes require a valid session cookie (`laravel_session` by default).

### CSRF protection

State-changing requests from the browser **must** include a valid CSRF token:

- Hidden `_token` field in HTML forms, or
- `X-CSRF-TOKEN` header (used by Axios in the article editor).

**Missing or invalid CSRF:** `419` Page Expired.

### Logout

```http
POST /logout
```

Requires authenticated session + CSRF token.

### Roles

| Role | Value | Capabilities |
|------|-------|--------------|
| Admin | `admin` | Full access: sites, users, authors, all articles |
| Writer | `writer` | Create/edit **own** articles only; cannot manage users, sites, or authors |

Authorization for JSON endpoints follows the same policies (e.g. only users who can create articles may upload images).

### JSON error responses (unauthenticated)

When a JSON-capable request is made without a session:

```http
HTTP/1.1 401 Unauthorized
```

HTML requests redirect to `/login`.

## 2. Remote site receivers (API key)

Used by: outbound CMS publishing (content, authors, categories)

### Header

```http
X-API-Key: cms_<40-character-random-string>
```

### Key format

- Prefix: `cms_`
- Generated by the CMS when a site is created or when an admin regenerates the key.
- Stored **encrypted** in the CMS database.
- Displayed once in the site detail view for admins to copy into the receiver configuration.

### Validation on the receiver

Receivers must compare keys with a timing-safe function:

```php
hash_equals(CMS_API_KEY, $incomingKey);
```

**Invalid key:** `401` with JSON body `{ "error": "Invalid API key." }`.

### Idempotency key (recommended)

The CMS sends:

```http
Idempotency-Key: <unique-string>
```

| Operation | Idempotency-Key format |
|-----------|------------------------|
| Publish article | `{article-uuid}-{site-id}` |
| Sync author | `author-{author-id}` |
| Sync category | `category-{category-id}` |

Receivers should store this value and treat duplicate deliveries as safe to upsert. The reference receivers persist the key but do not reject duplicates.

### Security recommendations

1. Use HTTPS only for all receiver endpoints.
2. Rotate keys via **Regenerate API key** in the CMS if a key is exposed.
3. Do not log full API keys or Base64 image payloads in production.
4. Restrict receiver URLs to POST (and optional GET for media serving in the content receiver example).

### What is NOT used

- No `Authorization: Bearer` tokens
- No Laravel Sanctum / Passport tokens
- No OAuth
- No API key on CMS internal JSON routes (session only)
